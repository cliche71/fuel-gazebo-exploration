# 与官方 FUEL 的对照

核对版本：`662dd23c7b52b258d3c4a0155ff6632118e8984f`。
来源：[FUEL 官方仓库](https://github.com/HKUST-Aerial-Robotics/FUEL/tree/662dd23c7b52b258d3c4a0155ff6632118e8984f)。

## 关于“后退重新观测”

官方当前版本没有“发现第一步走不出去，就自动后退”的规则。规划失败后会重新尝试。
探索途中可能返回此前已经看清的区域，画面上也可能表现为后退、转身或回头。
仅凭对过去画面的记忆，不能确定当时是哪一种情况。

官方启动时确实会先升高 1 米，再回到原高度。这段运动在此前的 Gazebo 迁移版中被省略了。
官方还保留过一段后退 1 米的代码，但已经全部注释，不会默认执行。

## 当前不能起步的原因

实际报告显示，起点周围的 26 条第一步路线全部经过未观测区域，未被障碍或地图边界挡住。
这与“探索到一半，返回看过的区域”不同。后者已有可供通行的观测结果。

官方示例把模拟相机放在机身位置；当前 VI 相机在机身前方约 11.6 厘米。
它们看到的近处空间并不相同。因此，更换办公室场景有助于对齐演示条件，但不能单独证明起步问题已经解决。
不得把整张办公室地图提前交给规划器，也不得把未观测区域直接改为空闲来掩盖问题。

## 已确认的迁移差异

| 项目 | 官方示例 | 之前的 Gazebo 版本 |
| --- | --- | --- |
| 场景 | office.pcd | 单个箱体的测试场景 |
| 启动准备 | 高度约 1 → 2 → 1 米 | 保持已验证的悬停 |
| 探索方式 | 飞行中持续更新路线 | 每段飞完、停稳，再规划 |
| 相机位置 | 与机身位置重合 | 机身前方约 11.6 厘米 |
| 失败后自动后退 | 没有 | 没有 |

之前的准备检查还额外要求起点所在格子已经空闲，这比官方搜索的条件更严格。
本次真正导致失败的是 26 条第一步连线都无法通过，不能把额外检查当作官方规则。

## 后续顺序与通过标准

1. **官方场景。** 本包只完成办公室布局转换；检查原始文件、场景中的障碍、起点附近空间。
2. **恢复官方流程。** 在独立版本中恢复飞行中更新路线的行为；启动设置和真实相机位置需要一起核对。不能只改一个开关，也不能把官方没启用的后退动作当作修复。
3. **实际探索。** 由观测建立地图；确认能生成第一段路线、连续执行后续路线、正常转向和返回，最后以实际位置和探索结果验收。

本包不更改现有 FUEL 源码，不恢复或启动任何准备运动，不启动自主探索。
当前环境没有 ROS/Gazebo，场景检查通过不代表已完成 Gazebo 飞行验证。

## 源码依据

- `fuel_planner/plan_manage/src/traj_server.cpp:492–502`：启动时上下运动。
- 同文件 `503–509`：被注释的后退代码。
- `fuel_planner/exploration_manager/src/fast_exploration_fsm.cpp:107–111`：失败后重新尝试规划。
- 同文件 `128–149`：探索中的后续路线更新。
- `fuel_planner/exploration_manager/src/fast_exploration_manager.cpp:124–237`：观察位置选择，以及搜索失败返回。
- `uav_simulator/local_sensing/src/depth_render_node.cpp:75–77,189`：官方 CPU 模拟相机的位置。
- `fuel_planner/path_searching/src/astar2.cpp:45–61,97–110`：起点初始化、邻居和第一步连线检查。
- `fuel_planner/plan_env/src/sdf_map.cpp:313–316` 及 `raycast.cpp:374–379`：观测更新不会保证相机所在格子本身空闲。

## 需要的实际配置

保持原悬停仿真运行；在本包目录另开终端执行：

```bash
source ~/rotors_ws/devel/setup.bash
python3 scripts/collect_inputs.py
```

脚本只读取当前相机、里程计、无人机描述、控制参数，以及
`~/rotors_ws/rotors_vi_hover_fix` 内的启动配置。它不发布飞行指令，也不更改参数。
生成的 ZIP 用于核对真实设置，以免继续依据旧安装包猜测。
